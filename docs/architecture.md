# Forge Architecture

Status: initial draft. Describes boundaries only. Nothing here is implemented.

## Purpose

Forge is the orchestration layer of the Steel & Code platform. It sits between
external clients and models, decides which agent handles a request, gathers the
tools and context that agent needs, and returns a result.

Forge is not a model provider, not an automation scheduler, and not a website.

Forge is **terminal-first**. The primary human interface is the command line,
with a terminal UI as the richer form of it. Everything else Forge exposes is
secondary and exists to serve a machine, not a person.

## Interaction surfaces

Ordered by priority, highest first.

### 1. Terminal — primary human interface

The primary human interface for Forge is CLI and TUI. A human operating an
agent should be sitting at a terminal, either on their own machine or attached
to a host where Forge runs.

A terminal-first Forge implies:

- Every action available in a TUI is also reachable from a plain command line,
  and vice versa. No capability lives only in the rich interface.
- Output is designed to be read by a person first and piped second. Human
  output stays readable; machine-readable output goes behind an explicit flag.
- Interactive prompting works. Tools can ask the operator a question and wait.
- Sessions are resumable and state is inspectable from a shell.
- No browser, no daemon rendering HTML, no login wall is required for core use.

### 2. Host — VPS and SSH

Forge is expected to run on a VPS and be operated over SSH. A dedicated
server, reachable by SSH, is a normal deployment target rather than an
exception.

This means:

- Forge must behave under a plain shell session: no assumption that a display,
  browser, or desktop environment exists.
- Long-running work must survive a dropped SSH connection, or at minimum fail
  loudly and leave recoverable state rather than dying silently.
- Configuration and credentials come from the environment on that host.
- A local workstation is the same product in a different place, not a special
  mode.

### 3. HTTP / API — secondary integration surfaces

HTTP and API interfaces are **secondary**. They exist so that other software can
drive Forge, not so that a person can.

Known consumers:

| Consumer | Why it needs HTTP |
| --- | --- |
| n8n | Schedules and webhooks are HTTP by nature. |
| Steel & Code website | A website cannot hold an SSH session. |
| Future services | Anything not in this repo. |

Because these are secondary, they carry no feature the terminal lacks. If
something is possible over HTTP, it is possible in the terminal first. An HTTP
surface is a remote control, never the place a feature is born.

One consequence is specific to the secondary path. Approval of a sensitive
operation needs an interactive human, and an HTTP caller is not one. So
approval-required operations **fail closed** when driven over HTTP — not
auto-approved, not queued. See [byte-tools.md](byte-tools.md) for the full
reasoning.

This is a deliberate limit on the secondary surface, not an oversight. An
unattended trigger can do the work that needs no approval and nothing else.

That rule is unchanged by Forge Workbench, and the reason is that Workbench is
not this surface. The rule above describes **machine-driven callers** — n8n, the
website, any future service — for whom an HTTP request genuinely is the whole
interaction. A machine has no human to ask, so there is nothing to wait for and
the honest answer is a refusal.

### 3a. Local interactive surface — `forge workbench`

`forge workbench` is a **local interactive human surface**: a browser page on
the operator's own machine, observing and steering one Byte run, with a human
present at the prompt. It is not a secondary integration surface and it does not
weaken the rule above.

The distinction is *who is being asked*, not *what protocol carries the answer*:

| | Machine-driven HTTP (n8n, website) | Workbench |
| --- | --- | --- |
| Caller | a trigger or a service | a person, at a browser, on loopback |
| Human available | no | yes |
| Approval-required | fails closed (`DENIED_UNATTENDED`) | prompts the person, waits for a decision |
| Answer transport | none exists | `POST /api/approvals/{id}` |
| Reachability | may be remote | `127.0.0.1` only |

A person answering in Workbench is exactly the interactive human that
`ApprovalChannel` has always assumed — a terminal channel and a browser channel
are two implementations of one question, not two different questions. What is
carried over HTTP is the *decision*, made by a human who is present, not a
*permission to act later without one*.

**Workbench creates no unattended approval route.** The properties that keep
that true are constraints, not intentions:

- Binds `127.0.0.1` only, with no host flag, so there is no configuration in
  which a remote host is reachable.
- Every request carrying a capability requires a per-process UI token
  generated by Forge, plus a same-origin check. A cross-site page cannot read
  the token, and no CORS headers are sent. The same-origin check is exact
  `Origin` on a state-changing POST, and on a read-only GET either an exact
  `Origin` or `Sec-Fetch-Site: same-origin` — a browser sends no `Origin` at
  all on a same-origin GET, so requiring one there would refuse the Workbench's
  own page. `GET /api/events` additionally requires a single-use stream ticket,
  because `EventSource` cannot set a header.
- One process has one active run. A browser tab observes a run; it never owns
  approval state, and a refresh re-derives state from the server rather than
  from anything stored in the tab.
- An approved outcome remains the existing single-spend capability in
  `forge/tools/approval.py`. Workbench resolves a wait; it does not manufacture
  an approval, and the first valid response wins with later ones rejected as
  stale.
- An approval-required operation with no browser attached fails closed, exactly
  as it does with no terminal attached.

The one genuinely new thing Workbench adds is *deferred approval with resume*:
the runtime blocks a worker thread while the event loop keeps serving, so an
answer can arrive later than the question. That is new machinery in
`forge/ui/`, and it changes no policy semantics in `forge/tools/approval.py` —
`ApprovalChannel.present()` remains synchronous and still returns a plain
yes/no.

Static assets are served directly; no template engine and no multipart form
handling is involved. The optional dependency set is `fastapi` and `uvicorn`,
and the Forge core remains dependency-free.

**The route surface, and what each route is allowed to do.** Six routes, and the
distinction that matters between them is observation versus command:

| Route | Method | Kind | Guard |
| --- | --- | --- | --- |
| `/api/status` | GET | observation | token + read-only same-origin pair |
| `/api/models` | GET | observation | token + read-only same-origin pair |
| `/api/models/verify` | POST | command | token + exact `Origin` |
| `/api/run` | POST | command | token + exact `Origin` |
| `/api/approvals/{id}` | POST | command | token + exact `Origin` |
| `/api/events` | GET | observation | single-use stream ticket + read-only pair |
| `/api/orders` | GET | observation | token + read-only same-origin pair |
| `/api/orders/{id}` | GET | observation | token + read-only same-origin pair |
| `/api/orders` | POST | command | token + exact `Origin` |
| `/api/orders/{id}` | PATCH | command | token + exact `Origin` |
| `/api/orders/{id}/move` | POST | command | token + exact `Origin` |

`/api/health` is a seventh, deliberately outside this table: unauthenticated,
capability-free liveness that reveals nothing.

**Model health is an observation, and re-checking it is a command.** The
Workbench shows one indicator per capability tier, fed by `ModelRouter.status()`
verbatim. `GET /api/models` returns a server-side cached snapshot and *never*
probes: a page load, a refresh, or a reload cannot spend a provider request or
present a credential, because a browser-reachable read that opened sockets would
make "open the tab" a billable action. `POST /api/models/verify` is the only way
to make the server contact a provider after startup, and it is a command for the
same reason it is a POST — it reaches providers, so it takes the strict
exact-Origin rule and cannot be triggered from a page Forge did not serve. It
also refuses while a run is in flight: a verification pass opening sockets from
inside a process that is already executing would be an incidental side effect of
running Byte, and health checking must never be one.

`forge workbench` performs one verified health pass at startup so the first page
load shows a checked answer. After that there is no polling anywhere — the page
re-reads the cache on load and on visibility change, and only the operator's
Re-check presses anything. Credentials live in the server process and in the
verifier factories; no response, and no browser state, carries one.

The frontend does not decide health. `forge/ui/static/health.js` maps the
backend's health string to a glyph and a word, and structural tests fail if it
ever compares a health value, assigns one, or names a model or provider. See
[model-registry.md](model-registry.md) for the full contract.

### 3b. The Order Board — durable workspace state

The Order Board is a Kanban view inside the Workbench: six fixed columns, one
Order each, moved between states explicitly. It is the first Forge surface to
persist anything, and the decisions below are recorded because they are the ones
a later reader would otherwise have to reverse-engineer.

**It is workspace-scoped, at `<workspace>/.forge/orders.json`.** Not under
`~/.forge/`, and not configurable. An Order belongs to the project it was made
in, so the board travels with the repository the same way durable project memory
does — see [agent-contract.md](agent-contract.md) for the reasoning, and for why
a human-readable tracked file was chosen over a database there. The same ruling
applies here. The path is derived from the workspace root inside
`OrderStore.__init__`, so no caller can aim it elsewhere; a run cannot read or
write orders belonging to another workspace.

Orders are **not secrets**. Byte can read the file through ordinary workspace
access, and that is accepted rather than worked around.

**Persistence is a whole-document atomic JSON write under one lock.** Every
mutation serialises the entire board, writes it to a temporary file in the same
directory, `fsync`s it, and moves it into place with `os.replace`. The temp file
is in the same directory because a rename across filesystems is not atomic, which
would reintroduce the window this avoids. One `threading.Lock` is held across
each read-modify-write, so two concurrent writes cannot interleave and lose one.
Every store call runs through `asyncio.to_thread`, because a blocking write on
the event loop would stall the SSE stream and refuse an approval for as long as a
disk takes.

**A malformed file fails visibly.** It raises and the route answers 500 naming
the file. It is never replaced by an empty board: an empty board is a
trustworthy-looking statement that there is nothing here, and serving one over a
corrupt file would erase Orders silently and then tell the operator there is
nothing to do about it. A missing file *is* an empty board, which is a different
thing.

**`ORD` numbers are monotonic, gaps are valid, and an id is never intentionally
reused.** The next number is `max(stored counter, highest id present + 1)`,
reconciled on every load — never `len(orders) + 1`, which is correct only while
the file is exactly as Forge last wrote it. Taking the greater of two independent
facts about the sequence is the only rule that cannot reuse a number: an
operator who hand-adds `ORD-0042` without bumping the counter gets `ORD-0043`
next, and an operator who deletes orders by hand does not make the board start
reissuing numbers they have already seen. **A gap in the sequence is therefore
normal and is not a defect.** The worst outcome is a skipped number; the
alternative is two Orders sharing an id, which makes every later lookup
ambiguous.

**Movement is not editing.** `POST /api/orders/{id}/move` is the only route that
writes `status`, and `PATCH /api/orders/{id}` — the edit route — has no `status`
field in its body at all, so a title edit cannot become a transition by
accident. There is exactly one place to hang transition rules, approvals, or agent
automation later, without changing what an edit means.

The five routes, each split by whether it observes or commands:

| Route | Method | Changes an Order |
| --- | --- | --- |
| `GET /api/orders` | GET | no — returns every Order grouped by status |
| `GET /api/orders/{id}` | GET | no — returns one Order |
| `POST /api/orders` | POST | yes — creates one, answering 201 |
| `PATCH /api/orders/{id}` | PATCH | yes — title, priority, smith, description |
| `POST /api/orders/{id}/move` | POST | yes — status only |

The guards are the ones in the route table in section 3a: the two GETs take the
read-only same-origin pair, the three writes take exact `Origin`. Neither half of
the split is a formality — a forged `Origin` on a write is refused, and a read
with neither an `Origin` nor `Sec-Fetch-Site: same-origin` is refused too.

The workflow states are stable snake_case identifiers
(`orders_received`, `at_the_forge`, …); the blacksmith wording an operator reads
is presentation, lives in `board.js`, and can be reworded without touching a
stored Order. `GET /api/orders` publishes the backend's own `statuses` and
`priorities` so the page consumes that vocabulary rather than keeping a second
copy that can drift from it, and structural tests fail if the frontend names a
state.

**An Order has no execution semantics in this MVP.** Creating, editing, or moving
one starts no run, calls no model, spends nothing, and consumes no approval.
`forge/ui/orders.py` imports nothing from `forge/models/`, `forge/tools/`, or
`forge/ui/session.py`, and that is asserted on the module's import graph rather
than left as a comment. The board is inert by construction, not by a flag. There
is also deliberately **no delete, no drag-and-drop, and no history** — no
activity log, no blockers, no approvals, no model cost, no Git metadata, and no
test counts on an Order. Movement is an explicit set of buttons, one per state
the backend published, because a control reachable only by pointer gesture is
unusable by keyboard.

### 4. Provider-agnostic core

The core stays provider-agnostic. Forge does not embed vendor assumptions in
agent logic, workflows, or tools.

- Model access sits behind one interface in `forge/models/`. Swapping the
  gateway is a configuration change, not a rewrite.
- Agents declare what they need from a model, not which vendor supplies it.
- Tools do not call model providers directly.
- Workflows do not branch on a vendor name.
- No vendor SDK types appear in agent or workflow definitions.

This is what keeps a provider change cheap, and it is why the gateway is an
internal boundary rather than a set of scattered call sites.

### Forge — orchestration layer

Owns:

- Request intake and validation.
- Agent selection and delegation.
- Tool assembly and permissioning per agent.
- Step sequencing for multi-step work.
- Returned results and errors to the caller.
- **Credential handling.** Forge loads credentials and injects an allowlisted
  environment into processes it starts or provider clients it builds. Agents may
  use a credential through Forge-managed execution but may never read one, and
  secret values must not reach tool output, prompts, logs, memory, or any HTTP
  response.

Does not own: model hosting, scheduling, or the customer-facing UI.

The terminal is the reference implementation. If an orchestration behaviour is
hard to express at a shell prompt, the design is wrong, not the terminal.

Code lives under `forge/`; `forge/workflows/` is the top-level entry point for
orchestration logic, `forge/agents/` for agent definitions. The interface layer
a person drives lives in `forge/cli/`, and is the `forge` command. It classifies
operations and asks for approval; `forge check` still executes nothing.

`forge/tools/execution.py` is the one place Forge launches a process. It runs an
operation only when handed an already-approved outcome whose binding digest
matches the invocation exactly, and an approved outcome is a single-spend
capability that cannot be replayed — including by a second executor. The CLI
is called by `forge byte`, through `forge/tools/dispatcher.py` — the sole
runtime path to a process.

**There is no `forge exec` in v1, and that is a decision rather than a gap.** A
human running a command uses their own shell, which already grants everything
such a surface would and keeps their own judgement and undo history. An agent
requesting execution goes through the one pipeline — classify, secret checks,
approval, execute — and that pipeline is not exposed as a second entry point,
because two entry points mean two policies once the second one needs an
exception the first is too slow to take. A human-facing execute verb would also
be one `--yes` flag away from voiding the approval model. The reasoning and the
only acceptable shape for a future one are in
[byte-tools.md](byte-tools.md).

`forge byte` is therefore the only Forge surface that executes, and it executes
only what the dispatcher decided was permitted. `forge check` still stops at the
approval step.

### 4b. Agents — configuration, and a registry of them

Forge has more than one agent. Byte is the reference *shape*; Neighbor is the
second instance, and it is the one that proves the shape generalises: it
answers every contract field differently and lands in the same runtime.

**An agent is a value.** `forge/agents/profile.py` holds `AgentProfile`, a
frozen dataclass. Byte (`byte.py`) and Neighbor (`neighbor.py`) are each one
instance. There is no `Agent` base class, no subclass, and no per-agent branch
in the runtime — `AgentRuntime` holds a profile and never learns which agent it
is serving. Adding an agent costs a profile, not a class and a conditional.

`forge/agents/registry.py` is the single place a name becomes a profile.

Three properties, each a decision:

* **Explicit membership, not discovery.** No entry-point scan, no directory
  walk. An agent that appears because something happened to be imported is an
  agent nobody chose. Adding one is an edit to `AGENTS`.
* **Unknown name is a value, not an exception.** `get_agent` returns `None`, so
  a typo and a broken install are different failures.
* **No routing intent in the registry.** The registry holds profiles, never a
  model, a tier, or a task kind.

**A task kind is not a profile field, and this is the load-bearing
distinction.** A profile cannot assert its own purpose: the *caller* knows what
it is asking the agent to do, and the same profile could legitimately be routed
differently by two surfaces. So `AgentProfile` carries `model: str | None` and
nothing else model-shaped, and it is `None` for every agent. Byte's task kind
is `coding`; Neighbor's is `conversation`; both live in `forge/cli/main.py`
beside the surface that knows them, and both are resolved through
`forge/models/` at run time.

**One verb per agent.** `forge byte` and `forge neighbor` are separate
subcommands rather than a `--agent` flag, so every existing spelling of
`forge byte` is unchanged and a third agent does not force a redesign of the
first. Both are thin wrappers over one shared `_run_agent`; they differ only in
the profile passed and the task kind it routes under.


### OpenRouter — model gateway

Single point of access to language models. Forge talks to a model gateway and
to nothing else when it needs an LLM call.

Why a gateway: one API surface, one place to switch or fall back between models,
and centralized usage and cost tracking. It also gives Forge one place to
enforce provider-agnosticism — nothing above this boundary knows a vendor name.

OpenRouter is the current intended gateway. The abstraction is the point, not
the vendor: no OpenRouter client exists yet, and when one is added it goes
behind the interface in `forge/models/` so the rest of Forge never depends on
that SDK. A different provider should be reachable by changing configuration.

### n8n — automation and triggers

Owns *when* things happen. Scheduled jobs, inbound webhooks, third-party events.

n8n does not run agents and does not hold business logic. It decides that
something should be triggered and hands the payload to Forge. Forge does not
schedule its own work.

n8n reaches Forge over a secondary HTTP surface, because webhooks and schedules
are HTTP by nature. That surface carries no capability the terminal lacks.

Integration direction is inbound (n8n calls Forge). Outbound notification from
Forge back into n8n is possible later but undecided.

### Byte, Ember, Fin — agents

Agents are the workers Forge orchestrates. Each is a role, not a separate
service.

| Agent | Role | Surface |
| --- | --- | --- |
| Byte | Software engineering agent. Builds and maintains code. | Terminal, primary |
| Ember | TBD. | TBD |
| Fin | TBD. | TBD |

All three run on the same Forge runtime and differ by configuration: model,
tools, instructions, permissions, workspace, and memory scope. Byte is the only
one specified so far; Ember and Fin are planned names with no agreed scope.

**Permissions are not part of that per-agent freedom.** Every agent runs under
one Forge-wide safety baseline — the workspace boundary, the two-tier secret
classification, and the command classifier, with automatic / approval-required /
denied decided by an explicit rule table and approval-required as the default for
anything unrecognised. Byte is its reference configuration. An agent may be
configured **narrower** than the baseline; nothing in the configuration path can
widen it, and there is no agent-level "allow extra" or trust override in v1. Any
future widening is a change to the baseline itself, reviewed like any other
policy change.

The per-agent fields are defined in [agent-contract.md](agent-contract.md). No
agent logic, prompt, or executable definition exists.

### Steel & Code website — external client

The public-facing site. It consumes Forge; Forge does not own it and does not
depend on its internals.

The website is an external client of a secondary Forge interface. It cannot
hold an SSH session, so it arrives over HTTP — but it gets no capability that
the terminal does not also expose. The interface is not defined yet; defining
it is one of the next steps, because it fixes the contract everything else is
built behind.

## Data flow

Illustrative, for the intended shape. None of this exists yet.

Primary path, a person at a terminal:

1. The operator invokes an agent from the command line, or starts a TUI
   session, on a local machine or a Forge host over SSH.
2. Forge resolves the agent contract: model, tools, permissions, workspace,
   memory scope.
3. The agent requests a model call; Forge calls the model gateway.
4. The model returns; the agent may call a permitted tool or continue looping.
5. Memory and workflow state are updated; output is rendered for the operator.

Secondary path, software driving Forge over HTTP:

1. A trigger fires (n8n schedule, webhook, or website request).
2. Forge receives the request and picks an agent from its contract.
3. Steps 3 through 5 proceed as above, minus the human rendering step.
4. The result returns to the caller as structured data.

The two paths converge on the same orchestration core. Only entry and rendering
differ.

## Explicitly out of scope for this pass

- OpenRouter integration, or any model provider client.
- n8n wiring.
- Agent logic, prompts, or execution.
- A **database**. The one durable store in Forge is the Order Board's
  workspace-scoped JSON file (section 3b), which is deliberately not a database
  and deliberately not general-purpose. A shared multi-user store, a server-side
  database, or a background job runner is still out of scope.
- Public API and its schema.
- Python classes for the agent contract.
- Tool implementations.
- Dependency installation by agents. Forge v1 assumes the project environment
  is already provisioned.
- Unattended approval over HTTP. Deferred approval with resume exists only in
  `forge workbench`, where a human is present; see section 3a.
- Execution triggered by an Order, and any history on an Order. See section 3b.

## Consequences worth stating

These are consequences of terminal-first, not preferences.

- Testing favours plain functions over framework objects. The contract can be
  validated from a shell without standing up a server.
- Debugging favours readable logs and inspectable session state over dashboards.
- Deployment stays small. A VPS running a CLI is a smaller operational surface
  than a service with a web tier.
- Network access is optional, not assumed. A Forge host with no inbound HTTP
  reachable is still fully usable over SSH.
- Secrets live at the orchestration layer, not in the agent's reach. An agent
  gets capability without getting values, which is what makes it safe to run
  unattended.

## Design decisions recorded

Decisions taken during design that are not obvious from the surface list, and
would otherwise be re-litigated:

- Terminal-first, HTTP secondary (see Interaction surfaces).
- One binary, agent name as a subcommand — `forge byte`, later `forge ember`.
  Not one binary per agent.
- The terminal entry point classifies and asks; `forge check` still executes
  nothing.
- Execution lives in exactly one module and requires a claimed approval. There
  is no second path to `subprocess`, and no `forge exec` in v1.
- An approved outcome is a single-spend capability, and it is bound to the exact
  invocation it approved.
- Permissions are a Forge-wide baseline, not a per-agent choice. Agents may be
  narrower; nothing may widen the baseline in v1.
- Automatic is an explicit rule. An unrecognised command is approval-required,
  so a classifier miss produces a prompt rather than silent execution.
- Executing repository code is approval-required — test runners and workspace
  scripts alike, because a repository is not a trust boundary.
- Model access behind one gateway interface; no vendor names above it.
- Agents are configuration, not classes or services. Byte is an `AgentProfile`
  value, and the runtime that serves it does not know its name.
- The model decides what it wants to attempt; Forge decides whether it is
  allowed. The runtime holds no classifier, `Approver`, or `Executor`.
- Agents may use credentials but never see them.
- Approval is per-operation; no blanket approval in v1.
- Approval-required operations fail closed when unattended.
- `forge workbench` is a local interactive human surface, not a secondary
  machine-driven one. It fails closed exactly as the terminal does, and it
  creates no unattended approval route (see section 3a).
- Server -> browser activity travels over SSE, not WebSockets. Approvals
  arrive as a POST, because a decision is a command rather than an event.
- Observational events are emitted through one optional `EventSink` hook and
  carry bounded, sanitised data. A sink observes; it decides nothing, and no
  surface scrapes logs or reaches into runtime internals to find out what
  happened.
- The UI dependency set is optional and minimal (`fastapi`, `uvicorn`); the
  Forge core stays dependency-free.
- Memory is a Forge-wide architecture, not a per-agent choice.
- Memory is session-only in v1; durable project memory designed, disabled.
- The project environment is provisioned by a human, not by the agent.

## Open questions

- What is the session model: persistent resumable sessions, or one-shot runs?
- Does the website get a different interface from n8n, or one shared secondary
  surface with per-consumer credentials?
- Are Ember and Fin single agents or families of agents?
- Which model capability levels should the gateway expose as configuration, and
  which model does each agent default to?
- Does Forge ever call out to n8n, or only receive from it?
- Are the security classification lists in
  [byte-security-classification.md](byte-security-classification.md) accepted
  as written? Settled: two-tier secret sources, wildcard deletes denied, inline
  code approval-gated without analysis, network commands approval-gated,
  Linux-only scope, and — from the permission-model pass — an explicit ALLOW
  table with approval-required as the default for unrecognised commands, plus
  approval-required for workspace-local executables and for anything executing
  repository code. **The code has not caught up to the last three yet**; see the
  gap table in [byte-tools.md](byte-tools.md).

**Resolved:** memory scope is a single Forge-wide decision, not a per-agent one,
with Byte as the reference agent. Session memory in v1; durable project memory
designed and disabled; personal memory out of scope. Ember, Fin, and future
agents inherit the architecture unless a future contract explicitly changes it.
The full model is in [agent-contract.md](agent-contract.md).

### 4c. Four model mechanisms, deliberately distinct

Model selection in Forge is four separate things that are easy to conflate.
Keeping them apart is what stops "manual selection" from quietly becoming a
fifth thing that owns models.

| | Decided by | Lifetime | Where |
|---|---|---|---|
| **Agent identity** | the contract | permanent | `AgentProfile` — name, instructions, allowed tools |
| **Routing default** | the registry, from task + difficulty | per resolution | `[routing.tasks.*]` |
| **Invocation override** | a human, per run | one invocation | `--model ID`, `$FORGE_MODEL` |
| **Health verification** | the provider, on request | a snapshot | `Availability`, `forge models status --verify` |

Precedence for a run is **override → routing**, both above supplying a provider:
`--model ID` → `$FORGE_MODEL` → registry by task/difficulty. An override is an
*invocation-level* decision and is deliberately narrow about what it is:

* **not** an `AgentProfile` field — `model` stays `None`, and there is no
  `override` or `preferred_model`. A per-agent standing preference would compete
  with routing and remove the registry as the single source of the default.
* **not** persistent — nothing is written, so no run can become the next run's
  default.
* **not** a registry mutation — no tier, slot, or config file changes.
* **not** a trust signal — selecting a model does not assert it works.
* **not** a fallback trigger — an override resolves to exactly what was named,
  because no tier was consulted to fall back *from*.

**An override is reported on, never validated against.** It short-circuits
before the registry is read, so a broken configuration cannot block a run —
that is the escape hatch's entire purpose, and an operator reaching for it is
usually doing so *because* the configuration is broken. Where the registry *is*
readable, Forge emits a non-blocking stderr advisory for a model that is
unknown, `enabled = false`, or known-unusable. The warning never changes the
outcome, and silence when the registry cannot be read is deliberate. A warning
that could fail a run would be a second policy.

Verification stays where it has always been: an explicit operator act that
supplies facts about reachability and never selects a model. Making a run
depend on a verification pass would put a network call in the path of every
invocation.

Full precedence, advisory table, and the routed/override asymmetry are in
[model-registry.md](model-registry.md).

**What does not vary per agent.** The safety stack is shared and is not
configurable: same classifier, same secret rules, same approval layer, same
executor, same `AgentProfile` narrowing rule (an agent may be *narrower* than
the baseline, and no configuration path can widen it). Neighbor's difference
from Byte is in its instructions, not in its permissions — including a
multi-agent boundary that tells it to leave other agents' work alone, which is
an instruction and not a permission.

The per-agent contract, including Neighbor's settled fields and the reasoning
behind each, is in [agent-contract.md](agent-contract.md).
